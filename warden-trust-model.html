Why Trust This Recording?

The Warden attestation policy — and every way we know to cheat it

Attestable Audio Recorder · GrapheneOS · Pixel 10a · Titan M2 · Warden Supreme 1.1.4

The Claim We Are Making

"This audio and video was signed, chunk by chunk, by a key that lives inside the Titan M2 chip of a specific Pixel, on behalf of our unmodified app, running on an unmodified OS — and nobody changed a byte afterwards."

✅ What this deck argues

Every part of that sentence is now checked cryptographically by Warden against a policy we control, not by reading names off a certificate.

❌ What it does not claim

That the sound reaching the microphone was real, or that the recording was made recently. Those are the cheap attacks, and we'll be honest about them.

What the Verifier Receives

One manifest plus the raw PCM chunks and MP4 segments. Nothing else. No trust in the phone's word.

Who signed what

The leaf is signed by a key that only exists inside the Titan M2. That key's certificate is signed by Google, freshly, every couple of weeks. Google's root is pinned inside Warden.

Why the short validity matters

Leaked device attestation keys ("keyboxes") are a real problem in the Android ecosystem. Short-lived, remotely provisioned certificates plus Google's revocation list limit the blast radius of a leak.

What the Attestation Extension Says

Real output from server --inspect on the recording above. Every line is inside the leaf certificate, signed by the Titan M2.

The app never wrote these values. The OS keystore fills them in, and the StrongBox chip signs them. "SelfSigned" is not a warning: it means the OS was signed by GrapheneOS's key, which the policy explicitly trusts.

The Warden Policy

AndroidAttestationConfiguration( applications = listOf(AppData( packageName = "com.attestable.recorder", signerFingerprints = setOf(70e16aec…49d9) // pinned release signing cert )), requireStrongBox = true, // Titan M2, not TEE, not software allowBootloaderUnlock = false, // also enables the two lines below verifiedBootKeys = grapheneOsKeys + VerifiedBootKey.OEM, revocation = listOf(GoogleDefaultLoaderConfig), supremeParser = true, ) Makoto(config).android.verifyKeyAttestationBlocking(certChain, challenge)

Chain

Path-validated to Google's root, every serial checked against Google's revocation list.

Extension

Challenge, security level, package, signer, boot state, boot key — all compared to policy.

Output

The attested public key. Chunk signatures are checked with that key and no other.

The Argument, Compressed

To produce a recording that passes strict verification and was not made by our app on real hardware, an attacker must do one of:

💎 Break the Titan M2

Extract a key from a chip designed against physical and side-channel attacks. Nation-state budget, per device.

🏛️ Compromise Google's attestation PKI

Or obtain a leaked device key before Google revokes it. Rare, noisy, and short-lived by design.

🐛 Exploit the keystore / bootloader

A zero-day that lets a modified OS boot as "Verified", or lets one app impersonate another to KeyMint. Patch level is attested, so this is bounded in time.

🎤 …or just fool the app

Give the legitimate app fake input. This needs no crypto at all — and it is where the honest discussion starts.

Cheat #1 — Feed the Microphone

The attack

Play a deepfake, a TTS clip, or an edited conversation through a speaker next to the phone. Press record. Every check passes, because every check is true: real chip, real app, real OS, real signature.

Cost: a speaker Detected: never, by attestation

Why attestation can't help

Attestation proves who signed and on what. It says nothing about the physics in front of the microphone. This is the fundamental ceiling of the whole approach.

Mitigations (none cryptographic)

  • • Liveness: prompt-response, verifier-issued spoken nonce
  • • Multiple witnesses: several attested devices, cross-check
  • • Context: attested time, location, other sensors
  • • Forensics on the audio itself

Cheat #2 — The App Picks Its Own Challenge

The attack (before the fix)

If the app draws its own 32 random bytes and writes them into the manifest, Warden's challenge check always passes — the same party chose both sides. A key generated months ago is indistinguishable from one generated today.

Cost: none Status: closed 2026-09-12

The fix (implemented and tested on the Pixel 10a)

server issue-challenge → C, 30-min TTL, stored adb … --es challenge C or typed into the app generateKey(challenge = C) manifest: challenge_source=verifier server … --require-issued-challenge ✅ key generated after 19:32:53Z; challenge consumed ❌ second recording with C: "already used"

Freshness is now a lower bound the verifier chose itself. Remaining assumption: the store is local to one verifier instance.

Cheat #3 — Modified OS on an Unlocked Bootloader

The attack

Unlock the bootloader, flash an OS that lies. The Titan M2 still signs honestly — but the package name and signer in the extension are supplied to it by the OS keystore. A malicious OS can claim any app generated the key, inject audio into AudioRecord, or sign arbitrary data with the app's key.

The hardware's answer: it also records bootloader locked and the verified-boot key the bootloader reported. Warden rejects the attestation unless the OS came from a trusted key.

What we saw on the test phone

before relocking: ❌ Attestation rejected by Warden Reason: Bootloader not locked after relocking: ✅ Bootloader locked: true Verified boot state: SelfSigned (GrapheneOS Pixel 10a)

Strict mode was right to reject the unlocked phone. The demo flag --allow-unlocked-bootloader turns off the lock, boot-state and boot-key checks in one go — which means the package/signer lines can no longer be trusted either. Never use it outside a demo.

Relocking the bootloader (a factory reset) fixed it; GrapheneOS's published boot keys were already trusted.

Cheat #4 — A Different App, or a Different Build

Same package name, other signer

Rejected. The signer fingerprint is in the extension and pinned in the policy. Re-signing an APK changes the fingerprint.

Our key, modified code (the "evil twin")

Passes. Tag 709 proves who holds the key, not what ran. The release build now uses a dedicated non-debug key, but that key is still a file on a laptop.

Fix: an encumbered key in a TEE/HSM that only signs reproducible canonical builds — turns signer-binding into code-binding without leaving stock GrapheneOS.

Old, vulnerable version

The extension carries the app's versionCode and the OS patch level. The policy does not yet enforce minimums (appVersion, patchLevel in Warden). Easy to add.

Attestation binds the key to an identity. Whether that identity behaves is a question of code review, reproducible builds and transparency — not of cryptography.

Cheat #5 — Leaked Device Keys and Hardware Attacks

🔓 Leaked attestation keys ("keyboxes")

Real in the wild for TEE-level attestation: extracted keys let emulators pass integrity checks. StrongBox keys are far harder to extract, this chain uses remotely provisioned two-week certificates, and Warden queries Google's revocation list on every run.

Hardening not yet enabled: requireRemoteKeyProvisioning = true rejects chains from factory-provisioned keys entirely.

💎 Attacking the Titan M2

Fault injection, decapping, side channels. This is the threat model the chip was built for; a working attack is worth far more than one faked recording. Treat as out of scope, but say so.

Note also: firmware bugs below the OS (bootloader, TEE) would not be visible to attestation until patched — the patch level in the extension lets you refuse old firmware.

Cheat #6 — Attack the Verifier Instead

Weak flags

--allow-unlocked-bootloader disables all boot checks --allow-tee accepts non-StrongBox keys --skip-revocation-check accepts revoked devices (no --require-issued-challenge) accepts app-chosen challenges

The policy is only as strong as the flags used. A "temporary" demo flag in a production script is a full bypass.

Trusting the wrong things

  • • Don't read the public key off the leaf yourself — use the key Warden returns (the old verifier got this wrong)
  • • Don't trust subject names like "O=StrongBox"; trust the attested security level
  • • Pin the signer; don't just check the package name
  • • Log the full attestation summary with every verdict so verdicts are auditable

Bottom Line

With the Warden policy, a passing recording means: a specific Pixel's Titan M2 signed these exact bytes on behalf of our app, signed by our key, on an OS booted from Google's or GrapheneOS's key, and nobody has touched them since.

Convincing because

Every claim is asserted by hardware and chains to a public root; Warden checks each one against an explicit policy and we only trust the key it hands back.

Not convincing about

Whether the sound was genuine. That needs liveness and independent witnesses — not more cryptography on the phone.
