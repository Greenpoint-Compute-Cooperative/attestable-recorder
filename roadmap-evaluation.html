What Already Runs on the Pixel 10a

📱 Capture app

GrapheneOS, bootloader locked. Audio in 5-second chunks, each hashed and signed inside the Titan M2 (StrongBox). Accepts a verifier-issued challenge (text field or adb intent).

🛡️ Warden verifier

Chain to Google root + revocation list; challenge, StrongBox, package, APK signer, bootloader lock, GrapheneOS verified-boot key. Chunks checked with the attested key.

🕐 Freshness

Single-use, time-limited challenges issued by the verifier; consumed on success. Proven end to end today: strict policy pass, second use rejected.

A4 — Video: the Pixel Is a Better Base Than the Pi

Roadmap plan

Raspberry Pi 5 + Camera Module 3, c2pa-rs per-segment signing. Named gap: a $30 TC358743 HDMI→CSI-2 adapter injects synthetic video and the Pi signs a valid C2PA manifest for it. "Named, not closed."

On the Pixel

Sensor → ISP over an internal MIPI link on the board; no exposed CSI connector. Injection needs a modified OS (caught by verified boot) or physical rework. Not closed, but the cost rises from "buy an adapter" to "desolder a phone".

CameraX → MediaCodec H.264 → fMP4 segments (2–5 s) → SHA-256 → sign in StrongBox → manifest same verifier, one new chunk type · C2PA wrapper as a post-process (c2patool) if the wire format matters

That last sentence is the product hook: an attested source is the strongest possible answer to it.

Why hash-what-you-received matters

It proves the audio the room transcribed is the audio the Titan M2 signed — not merely that some signed audio exists somewhere. It also makes the 100 ms alignment criterion moot: alignment is by content hash, not clock.

Build It as Generalized Tooling

vibecode-room is one consumer, not the design centre. Three separable pieces:

1 · attested-capture Android library

Extract AttestationManager + chunk signer. Sources: AudioRecord PCM, CameraX fMP4 segments. Sinks: file manifest, live stream. API: openSession(challenge), sign(chunk). Optional redacted-transcript binding for A1 #18.

2 · attested-capture-verifier

The Warden verifier + HTTP surface + a policy file (package, signers, StrongBox, boot keys, patch level, RKP). JVM jar for room nodes; Android APK for the second-phone bystander path after a spike.

3 · Wire spec (manifest v3)

Session header (chain, challenge + source, device claims) + chunk records (type audio|video, index, ts, hash, sig). Same document as a file, a WebSocket stream, or a C2PA assertion.

Order for the October demo: spec → streaming audio → HTTP verifier → wall badge → video segments → second-phone verifier.

What the Pixel Does Not Solve

Track B, entirely

No tamper-evident enclosure, no hardware recording indicator. The phone's light is software — attested software, but software.

Sensor authenticity

Attestation proves which device and app signed the bytes, never that the mic heard a live human or the camera saw a real scene. "Named, not closed" applies unchanged.

Static, backend-free verification (#19)

Needs an Android verifier app or a LAN service until attestation verification exists in JS/WASM. Don't write that in-sprint.

App behaviour

The release build is signed with a dedicated key, but a signer proves who holds the key, not what ran. Reproducible builds + an encumbered (TEE/HSM) key are still required before a third party can trust the app, not just the chip.
