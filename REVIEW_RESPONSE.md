The review ("Two phones, two attested recorders, one wall") read commit `d830162`, the state of
this repo before any of today's work. It is accurate about that commit. This file goes through
its findings in the reviewer's order and states what changed, what did not, and why.

## Findings on the evidence structure

| Finding | Status now |
|---|---|
| Independent per-chunk signatures let a signer silently drop the middle | **Fixed twice.** (a) v3 added a signed session record over the ordered chunk list, so truncation or reordering fails even when every remaining signature is valid. (b) v4 hash-chains each stream: every chunk's signed payload includes the previous chunk's hash, so a missing middle chunk is caught even if the session record is absent (crash mid-recording). Both are tested and were exercised against a real recording. |
| Gap records for every stall | **Partly.** The verifier reports gaps, missing indexes and audio/video skew as warnings from the signed timestamps and durations. The app does not yet write explicit gap records when capture stalls; a stall shows up as a timestamp gap, which the verifier flags but cannot distinguish from a deliberately removed chunk unless the chain also breaks. |
| No per-record OS context | **Added (v4).** At start and stop the app snapshots: `debuggable`, install source, enabled accessibility services, number of *other* apps recording audio, device model, OS build, security patch. The canonical encoding is digested into the session record's signed payload, so it cannot be edited afterwards. It is app-observed, hence exactly as trustworthy as the app + OS the attestation pins — which is the reviewer's own point about "the OS state around the samples is the evidence". Not yet per chunk; only per session. |

## The wall: signer ≠ code

The reviewer's evil-twin result is accepted in full and was already the "malicious build with our
signing key" row in the threat matrix: tag 709 proves who holds the signing key, not what code ran.
Moving to a release key changes *who* that is (no longer "anyone with the Android SDK"), not the
shape of the claim.

Of the two routes offered, this project should take the **encumbered signing key**: a key held in a
TEE (or an HSM with a policy) that only signs reproducible, canonical builds. It keeps stock
GrapheneOS, needs no OTA-key obligation, and works precisely because tag 709 carries the signer
digest. The re-signed-OS route is not planned here; the roadmap's A2 epic covers it as a separate
track, and the reviewer's own /data-shadowing finding shows its cost.

Prerequisites this repo still owes for that route, in order:

1. Reproducible build (pinned toolchain, deterministic APK) so the canonical build is definable.
2. The release key moved out of `release.jks` into a TEE/HSM signer with a "canonical build only"
   policy; publish the signer fingerprint alongside the source.
3. Warden `appVersion` floor so old builds signed by the same key are rejected.
